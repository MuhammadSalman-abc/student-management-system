# Student Management System

The project is being rebuilt incrementally from the architecture in [SYSTEM_DESIGN.md](./SYSTEM_DESIGN.md). The current implementation is a React/Vite client and Express/MongoDB API.

## Requirements

- Node.js 20.19+ or 22.12+ (required by the installed Vite and Mongoose versions)
- MongoDB 7 replica set (including a single-node local replica set) or a compatible managed deployment; student/account identity edits use multi-document transactions

## Local setup

1. Install frontend dependencies: `npm --prefix client-old/client install`
2. Install backend dependencies: `npm --prefix server-old/server install`
3. Copy `server-old/server/.env.example` to `server-old/server/.env`. Generate a fresh JWT secret with `node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64url'))"` and put it in `JWT_SECRET`; the API refuses to start with an empty or known example secret. Keep `JWT_COOKIE_MAX_AGE_MS` no greater than the `JWT_EXPIRES_IN` lifetime. Set `DB_CONNECT_TIMEOUT_MS` between 1000 and 120000. Keep `CLIENT_APP_URL` on an exact origin listed in `CLIENT_ORIGINS`. Never commit `.env` or production secrets. For SMTP delivery, set `SMTP_HOST`, `SMTP_FROM`, `SMTP_PORT`, and TLS options; set both `SMTP_USER` and `SMTP_PASS` for authenticated servers. Also generate a separate 32-byte base64 `EMAIL_OUTBOX_ENCRYPTION_KEY` for queued links, and keep it with SMTP credentials in the deployment secret store. Production requires SMTP configuration and TLS.
   Before using `backup:data`, generate a separate random 32-byte base64 key with `node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64'))"`, set `BACKUP_ENCRYPTION_KEY`, and retain that key in a secrets manager separate from the backup destination. The same key is required to restore new encrypted backups.
   For a non-local frontend/API deployment, copy `client-old/client/.env.example` to `client-old/client/.env` and set `VITE_API_URL` to the API's versioned base URL (for example, `https://api.example.edu/api/v1`).
4. Start MongoDB as a replica set (transactions are used by account, enrollment, attendance, and grade workflows). For local development, use a single-node replica set named `rs0` and set `MONGO_URI=mongodb://127.0.0.1:27017/student_management?replicaSet=rs0`; initiate it once with `rs.initiate()` in `mongosh`. If converting an existing standalone database, keep its existing data directory and take a verified backup first; do not initialize a fresh data directory as a substitute for preserving existing records.
5. Back up existing data and stop the API, then run `npm run ensure:indexes`. Resolve any duplicate report without deleting records, then run it again until the declared indexes are installed.
6. When moving existing student records into academic offerings, run `npm run migrate:legacy-academics` for a read-only inventory. Create a mapping JSON from its course/batch groups, preview it with `npm run migrate:legacy-academics -- --mapping server-old/server/legacy-academic-mapping.json`, then apply with `npm run migrate:legacy-academics -- --mapping server-old/server/legacy-academic-mapping.json --apply --actor-email admin@example.edu`. Keep the API stopped and use the same mapping file if resuming an interrupted run. The migration creates offerings and active enrollment rows only; it retains the old attendance and score snapshots without inventing dated attendance or grade records.
7. From the workspace root, run `npm run dev` to start the API and frontend together. Open the Vite URL it prints. Press Ctrl+C to stop both processes.

For separate terminals, use `npm run dev:server` and `npm run dev:client` from the workspace root.

Useful commands from the workspace root:

- `npm run build:client` — create the production frontend bundle.
- `npm run lint:client` — run the configured ESLint checks for the frontend and Electron shell.
- `npm run check:server` — parse every backend JavaScript source file without starting the API or connecting to MongoDB.
- `npm run start:server` — start the API after its database connection succeeds.
- `npm run ensure:indexes` — inspect existing records for duplicate values that would prevent a unique index, then create declared indexes if the database is ready. This command never deletes or merges records; resolve any reported duplicates through an approved data correction process and back up existing data first.
- `npm run migrate:legacy-academics` — read-only preview of existing course/batch groups; `--mapping <json-file>` validates a reviewed mapping, and `--apply --actor-email <active-admin-email>` performs resumable, transactional enrollment creation. It preserves legacy attendance/score snapshots and refuses unmapped groups or changed mappings.
- Mapping file format: `{"mappings":[{"legacyCourse":"exact dry-run value","legacyBatch":"exact dry-run value","courseCode":"CS101","courseName":"Course title","term":"Fall 2026","section":"A"}]}`. Choose the target course, term, and section from the institution's approved catalog; several legacy pairs may map to the same offering.
- `npm run backup:data` — create a compressed AES-256-GCM encrypted logical archive with a SHA-256 checksum in `BACKUP_DIR` (requires MongoDB Database Tools on `PATH` and `BACKUP_ENCRYPTION_KEY`). Stop the API first for a consistent maintenance backup. Store the backup and encryption key separately in approved secure storage.
- `npm run restore:data -- <backup-directory>` — verify the encrypted archive checksum and authentication tag, then restore only into an empty database selected by `MONGO_URI`. The same encryption key is required for new backups; older checksummed v1 backups remain restorable. It refuses to overwrite an existing database; after any restore error, keep the target isolated and retry with a new empty database.
- `npm run create-admin` — create the first admin account through a hidden-password terminal prompt (run only after configuring MongoDB).
- `npm run reset-admin-password -- --email <admin-email>` — interactively set a new hidden admin password; previous sessions for that account are revoked. Use only from an authorized operator terminal.

The API exposes `/health/live` for process liveness and `/health/ready` for database readiness. On an existing database, review a backup and run `npm run ensure:indexes` before deployment; it reports duplicate values that prevent unique indexes and makes no changes if it finds any. Resolve collisions with the institution's approved correction process, then rerun the installer. Do not drop, recreate, or replace an existing database to bypass index conflicts. Run `npm run create-admin` to provision the first administrator. Admins issue one-time student activation links from the roster; configured SMTP queues them transactionally to the institution-listed student email. The worker makes up to 10 delivery attempts with bounded backoff, discards expired or replaced links, and clears encrypted payloads after success or terminal failure. Links expire after 48 hours. When SMTP is unavailable outside production, admins can use the protected copy-link fallback; delivery status is shown in the roster. Public self-registration is disabled. Browser sessions use short-lived `HttpOnly` cookies and are revalidated against the API at startup; the browser does not store bearer credentials. Cookie-authenticated state-changing API requests require an exact allowlisted `Origin`; non-browser Bearer clients can omit it. Login requests are IP-rate-limited; wrong passwords increment a separate fixed 15-minute failed-login counter that clears after a successful login. Student invitation acceptance is also IP-rate-limited. MongoDB window increments are atomic, and rate-limit records expire automatically.

The versioned route catalog and core request shapes are documented in [server-old/server/openapi.yaml](./server-old/server/openapi.yaml) and served publicly at `/api/v1/openapi.yaml`. Keep this OpenAPI document aligned with route/controller changes; it is a reviewed contract file and is not generated automatically.

Every request receives an `X-Request-ID`. Unexpected server errors return the same ID in the JSON response; the server emits a structured error log with the request ID and route context, without logging the request body.

When an authenticated API request returns `401` because a session expired or was revoked, the client clears its session marker, returns to sign-in, and asks the server to clear the stale cookie. Expected `401` responses from anonymous sign-in/session checks do not trigger this behavior.

For deployment, set `CLIENT_ORIGINS` to exact origin URLs only (scheme and host, no path); production startup requires HTTPS and DNS hostnames, rejecting localhost aliases and IP literals. Set `CLIENT_APP_URL` to the frontend URL where invitation links should open, configure and verify SMTP delivery (`SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_REQUIRE_TLS`, `SMTP_FROM`, and optionally `SMTP_USER`/`SMTP_PASS`), and configure a separately managed `EMAIL_OUTBOX_ENCRYPTION_KEY`. Retain that key until queued links expire; rotating it early makes pending messages undecryptable. Use a same-site frontend/API deployment for the `SameSite=Lax` session cookie, set `NODE_ENV=production`, and set `TRUST_PROXY_HOPS` to the number of trusted reverse proxies in front of the API (leave at `0` when directly exposed). The cookie is marked `Secure` in production. The API applies HSTS in production. Use HTTPS end-to-end and do not expose MongoDB publicly.

The API disables implicit Mongoose index creation and refuses to start if declared indexes are missing or outdated. Back up the database and stop the API before running `npm run ensure:indexes`; it reports duplicates that prevent unique indexes and makes no changes when it finds any. This explicitly installs the sparse unique `student_number_unique` index and password-reset token/expiry indexes; existing student records without student numbers remain unchanged. Resolve collisions through the institution's approved correction process, then rerun the installer. Never drop or replace an existing database to bypass index conflicts. Use MongoDB Database Tools 100.3 or newer for `backup:data` and `restore:data`; the scripts keep the connection URI out of process arguments using the tools' protected config-file option and remove the temporary credential file after each command ([mongodump docs](https://www.mongodb.com/docs/database-tools/mongodump/), [mongorestore docs](https://www.mongodb.com/docs/database-tools/mongorestore/)). Run backups while the API is stopped, store them on separate encrypted storage, and restore into an isolated empty database with the same MongoDB major version as the source.

## Current usable workflows

- The admin dashboard shows a first-run setup guide for student records, course offerings, and enrollment; progress follows live backend counts and each action jumps to the relevant form.
- Admin can manage student records, create course offerings, enroll students, and withdraw enrollments without deleting their history.
- Individual student creation and CSV roster import both write their admin audit record atomically with the new student records.
- Student profile edits record the acting admin, student, changed field names, and timestamp in the same transaction as the update; field values and other personal data are not copied into the audit event.
- Student records support an optional institution-provided student number. Values are trimmed and stored uppercase; duplicates are rejected, and identifiers are never auto-generated. Legacy course, batch, attendance, and score fields are optional; active course placement is managed through offerings and enrollments. Legacy records and seven-column roster CSV files remain valid.
- Student list requests validate page, page size, sort, status, and filter shapes explicitly; malformed or repeated pagination parameters return a clear client error instead of silently selecting defaults.
- Admin can preview and import up to 100 students from the roster CSV template; validation, duplicate checks, record creation, and the aggregate audit event run as one transaction.
- Admin can archive course offerings only after their active enrollments are withdrawn, then restore them later without erasing published academic history.
- Admin can browse active enrollments and paginated enrollment history, and reactivate a withdrawn enrollment when the student and offering remain active.
- Enrollment creation, reactivation, and withdrawal are recorded with the acting administrator, student, offering, and timestamp in the same transaction as the enrollment change; admins can review these events in the audit trail.
- Assessment publication is recorded with its acting administrator, offering, assessment, released-result count, and timestamp in the same transaction; draft grades and individual scores are not copied into the audit event.
- Attendance finalization is recorded with its acting administrator, offering, session date, marked-student count, and timestamp in the same transaction.
- Admin can issue, copy, and reissue a 48-hour student account invitation; the roster shows token-free pending, expired, replaced, linked, disabled, and repair/conflict statuses, and activation creates the login and links it to the pre-provisioned student record atomically.
- Admins can suspend or reactivate an active student's linked account with confirmation; status changes and session revocation commit with an audit event, while academic and enrollment records remain unchanged.
- If a student forgets a password, an administrator must confirm identity through the institution's approved process before issuing a one-time reset link. With SMTP configured, the link is sent to the student's registered address; without SMTP in non-production, the protected admin view retains a manual-share fallback. The link expires in 30 minutes. Completion revokes all sessions and invalidates other reset links.
- Authentication uses only the server's HttpOnly cookie; client session state is held in memory and does not depend on browser storage being available.
- Students can set a preferred display name without changing the official roster identity, and change their password after verifying the current password; password changes revoke other active sessions.
- Authenticated password changes are recorded in the audit trail atomically with the password/session-version update; no password, token, or credential value is recorded.
- Students can upload, replace, and remove a profile photo. The browser resizes photos before upload; the server stores a private JPEG (up to 400 KiB) on the signed-in account and serves it only to that account. Previously saved browser-only photos are not uploaded automatically; they remain local until replaced or removed.
- Student profile, attendance, and result views resolve ownership through the explicit account link first; email matching is only used for legacy unlinked records.
- Editing a linked student's name or email updates the login identity in the same MongoDB transaction; duplicate emails are rejected without partially changing either record.
- Archiving a student updates the student record, active enrollments, and linked account access atomically while retaining academic history.
- Admin can open an attendance session for a course/date, mark the enrolled roster, save a draft, finalize it for student viewing, and submit corrections with an audit reason.
- Finalized attendance corrections and published grade corrections commit their audit entries and record updates in the same transaction.
- Assessment draft saves, publication, and published-grade corrections use revision checks so a stale administrator view cannot silently overwrite a newer grade set; the dashboard offers a reload action after a conflict.
- Attendance and assessment draft saves, release transitions, and enrollment roster mutations are transactionally serialized to prevent incomplete snapshots from being finalized or published during concurrent changes.
- Students can view their finalized attendance history and summary. The current summary counts `present` and `late` as attended and excludes `excused` from the rate denominator; confirm this policy with the institution before relying on reports.
- Admin can export finalized attendance by session date or published assessment scores by publication date, optionally filtered by offering. CSV output omits draft data, grade feedback, and actor identifiers, protects spreadsheet cells from formula execution, and is capped at 20,000 rows.
- Report exports select the bounded finalized/published parent records first, then join their marks/results; required indexes are installed through the explicit index installer and verified before API startup.
- Each successful academic CSV export writes an audit event with its administrator, filters, type, and row count; student names, emails, marks, and feedback are not duplicated into the audit log.
- Student archive and restore transitions record the acting administrator in the same transaction as account/enrollment updates.
- Admins can review and page through sanitized export, student import, invitation/password-reset issuance, account lifecycle, and student/course-offering archive/restore audit events from the dashboard. Invitation and password-reset tokens/links are never stored in audit events.
- Admins can switch between active and archived student records. Restore reactivates a linked account with a fresh token version (revoking previous sessions); withdrawn enrollments remain historical until staff explicitly re-enroll the student.
- Student lifecycle version writes serialize enrollment creation and invitation issuance against archive/restore transactions, preventing a concurrent request from linking an archived learner or leaving an active roster row behind.
- Admin can create assessments, save grades as drafts, publish only after every active enrollee has a score, and correct published grades with an audited reason. Students see only published assessment results.
- Admins can review paginated published-grade correction history with old/new scores, feedback, reason, actor, and timestamp; the history API returns bounded records and exposes no account credentials.
- Older assignment/final score fields remain as legacy profile snapshots. They are not treated as an official computed course grade because the institution's grading and weighting policy has not been confirmed.

New clients should use the versioned `/api/v1` base path. Academic APIs are under `/api/v1/academics`; student profile and attendance views are under `/api/v1/students/me` and `/api/v1/students/me/attendance`. The original `/api` path remains as a compatibility alias and sets `X-API-Deprecated: true`; all these routes require authentication and role checks.

The admin dashboard summary is a snapshot across all non-archived students, active offerings/enrollments, finalized attendance marks, and published assessment results; it has no date window. Attendance rate counts `present` and `late` over `present + late + absent`, excluding `excused`. Published score average is the unweighted mean of each published score normalized by its assessment maximum. CSV attendance exports filter by session date; results exports filter by publication timestamp in UTC.

## Project status

This repository is an active prototype-to-product rebuild. Review the system design's decisions and stakeholder checklist before production use. Execution of the reviewed legacy migration, remaining domain modules, complete role/ownership review, operational controls, and institution-specific policy decisions are still outstanding. Production SMTP credentials and delivery acceptance must be configured and verified in deployment. Email delivery uses a MongoDB transactional outbox with encrypted link payloads and bounded retries; delivery is at-least-once, so interruption after SMTP acceptance but before the success write can cause a duplicate email.
